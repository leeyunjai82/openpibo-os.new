# 03. 폐기된 추정 / 틀린 판단

계획 수립 과정에서 **추정으로 내렸다가 실측으로 뒤집힌 판단**들.

이 문서의 목적은 **같은 함정에 다시 빠지지 않는 것**이다.
특히 "안 쓰는 패키지 정리" 같은 지시를 받았을 때 dlib을 지우려 드는 것 같은
사고를 막기 위해 남긴다.

최종 갱신: 2026-08-27

---

## 1. dlib을 제거 후보로 분류 — **완전히 틀림**

### 처음 판단
> `dlib`, `openpibo-dlib-models` — `setup.py`엔 있는데 코드 import가 안 보입니다.
> 실사용처 확인 필요

### 실제
**얼굴 인식(구분)의 핵심이다.** 제거 대상이 절대 아니다.

| 용도 | 호출 |
|---|---|
| 68점 랜드마크 | `dlib.shape_predictor` — `landmark_face()` |
| 얼굴 임베딩 128-d | `dlib.face_recognition_model_v1` — `train_face()`, `recognize()` |
| 박스 변환 | `dlib.rectangle` — 3곳 |
| 객체 추적 | `dlib.correlation_tracker` — `vision_detect.py` |

### 왜 틀렸나
grep 패턴에 `dlib`을 넣지 않고
(`tensorflow|tflite|keras|ultralytics|mediapipe|onnx|torch|openvino`만 검색)
"import가 안 보인다"고 결론 냈다.

### 교훈
**검색 결과의 부재를 사실로 쓰기 전에 검색 조건 자체를 확인할 것.**

## 2. adafruit_ssd1306을 "구형 잔존"으로 분류 — **틀림**

### 처음 판단
> `adafruit_ssd1306` — 지금 ILI9341을 쓰는데 구형 SSD1306 드라이버가 남아 있습니다

### 실제
**파이보 현역이다.** `oled.py`의 기본 클래스 `Oled`가 `ssd1306.SSD1306_SPI`를 쓰고,
`booting.py`가 이걸 사용한다. 128×64 흑백.

세 클래스가 각각 다른 장치를 담당한다:

| 클래스 | 드라이버 | 대상 |
|---|---|---|
| `Oled` | SSD1306_SPI | **파이보** |
| `Oled7735` | ST7735S | 미사용 (소스 보존) |
| `OledByPiBrain` | ILI9341 | 파이브레인 |

### 왜 틀렸나
파이브레인이 ILI9341이라는 사실만 보고 파이보도 같을 거라 넘겨짚었다.
**두 보드가 다른 디스플레이를 쓴다는 게 애초에 통합 논의의 출발점이었는데도 그랬다.**

## 3. openvino 패키지를 "수백 MB"로 추정 — **과대**

### 처음 판단
> `openvino`(런타임)는 설치 후 **수백 MB 규모**로 추정됩니다

### 실제
**96 MB.** torch(400M), tensorflow(1.1G)와 비교하면 작은 편이다. 그대로 두면 된다.

`openvino-dev`는 메타패키지라 dist-info 356K만 존재하고 본체가 없다.
지워도 356K다. (단, 의존성으로 scipy 등을 끌어왔을 가능성은 별개)

## 4. LLM 상한을 "0.6B 이하" — **과소**

### 처음 판단
> 현실선은 **0.6B 이하, Q4, 컨텍스트 1024~2048**입니다.
> 1.5B는 이론상 들어가도 다른 기능을 전부 내려야 하고 초당 2토큰이라 수업에서 못 씁니다

### 실제
**Gemma 3 1B Q4가 이미 파이에서 구동 중이다.**

계산이 보수적이었다. Gemma 3는 로컬/글로벌 어텐션을 5:1로 섞어
(sliding window 512) KV 캐시가 동급 모델보다 훨씬 적게 든다.
llama.cpp가 SWA를 지원하니 그 이득을 받고 있다. 이걸 계산에 안 넣었다.

### 교훈
**"이론상 안 될 것"보다 "지금 돌고 있는 것"이 우선한다.**
현장에서 이미 동작하는 구성이 있으면 그게 실측이다.

---

## 5. 디스크 정리를 주요 명분으로 사용 — **근거 없음**

### 처음 판단
> **SD 카드 공간.** aarch64 TF wheel이 설치 후 500MB 이상입니다
> torch 계열, tensorflow 계열, openvino-dev, opencv 중복만 합쳐도 수 GB 규모로 추정됩니다.
> SD 카드 공간과 이미지 배포 크기, 굽는 시간에 직결됩니다

### 실제
```
/dev/mmcblk0p2   28G   16G   12G  58%
```
**12G 여유.** tensorflow 1.1G + torch 400M을 다 빼도 1.5G, 전체의 5%다.
16G → 14.5G면 이미지 굽는 시간도 체감이 없다.

### 결론
**의존성 제거의 명분은 RAM 하나뿐이다.**
그 기준으로 실익이 있는 건 **torch**(ultralytics 경유 상시 import)뿐이고,
나머지는 후순위다.

### 함께 폐기 — "사고 방지" 논거
> 학생이나 개발자가 무심코 `import pandas`를 하면 2GB에서 바로 문제가 됩니다

개발자 쪽은 분석으로 막을 일이지 패키지 제거로 막을 일이 아니다.
학생이 IDE에서 직접 치는 코드는 여전히 해당하지만, 급한 사유는 아니다.

## 6. 메모리 추정 전반 — **크게 빗나감**

### 처음 판단
> | 허브 (python + cv2 + numpy + picamera2) | 250~400 MB |

### 실제
**`Detect()` 인스턴스 하나가 789 MB.** 2GB의 40%다.

이 숫자 하나로 여러 결론이 확정됐다:
- LLM(800~950MB 추정)과 비전은 **절대 공존 불가**
- `ModelSlot` 교대가 선택이 아니라 필수
- 현재 `systemctl stop llama-server`로 서로 죽이는 구조는 **우연히 옳았다**
- 지연 로딩이 RAM에 직접 듣는 몇 안 되는 조치

### 교훈
**메모리 추정표는 실측 전까지 쓰지 말 것.** 자릿수가 틀린다.

## 7. RAG 검색을 BM25로 시작하자고 권고 — **철회**

### 처음 판단
> 교실용 지식베이스 규모에서는 BM25(키워드 검색)로 충분할 가능성이 높습니다.
> 메모리 0, 아이에게 설명 가능

### 실제
**e5-small 기반 RAG가 vapi-od에 이미 있고 실기 튜닝까지 끝났다.**

`db_routes.py`에 실기에서 깨져본 기록이 그대로 남아 있다:
```
# 처음 0.72 로 잡았다가 실기에서 맞는 질문(시간표)까지 걸러냈다 — e5-small INT8 의
```

**임베딩 모델이 같으면 이 값이 그대로 유효하다.** 처음부터 다시 맞출 필요가 없다.

### 교훈
**사내에 이미 있는 것을 먼저 찾을 것.** 두 경로를 만들 이유가 없다.

## 9. "vapi-od와 동일하게 = OpenVINO로 받기" — **오해 소지**

### 처음 판단 (부분적으로 오해를 부름)
런타임을 3종으로 수렴시키자는 방침이 "YOLO도 OpenVINO로"로 읽힐 수 있었다.

### 실제
**vapi-od도 ultralytics를 쓴다.**
```
class Yolo:
    """ultralytics + OpenVINO export 디렉토리 공용 래퍼."""
    def __init__(self, ov_dir, task=None):
        from ultralytics import YOLO
```

결정적 증거: `box.xyxy[0].cpu().numpy()` — `.cpu()`는 torch 텐서 메서드다.
**백엔드가 OpenVINO여도 결과는 torch 텐서로 나온다.**

### 결론
**두 축이 완전히 별개다:**

| 축 | 선택지 | 영향 |
|---|---|---|
| A. 래퍼 | ultralytics vs 직접 구현 | **torch 400MB** |
| B. 백엔드 형식 | ONNX vs OpenVINO IR | 속도, 일관성 |

**B만 바꾸면 400MB는 그대로 남는다.** "vapi-od와 동일하게"를 문자 그대로 하면
파이 메모리가 지금과 똑같다.

## 10. pose/body 특징의 모델 간 이식성을 "불가"로 단정 — **과했음**

### 처음 판단
> vapi-od에서 만든 학습 모델 파일을 파이로 못 가져옵니다.
> YOLO 특징으로 학습된 헤드라 movenet 특징을 넣으면 엉뚱한 답이 나옵니다

### 실제
특징의 성격에 따라 다르다.

| 모드 | 특징의 정체 | 이식성 |
|---|---|---|
| image (1280) | MobileNet이 **학습한 표현** | **없음** — 가중치가 다르면 전혀 다른 공간 |
| pose/body | **기하학적 좌표** 정규화 | **느슨하게 있음** |
| face (52) | mediapipe 블렌드셰이프 | **양쪽 동일** — 애초에 같은 모델 |

`_embed_body()`가 만드는 건 "어깨 중심에서 각 관절이 어느 방향으로 얼마나 떨어져 있나"다.
**물리적 의미가 있는 숫자**라 검출기가 달라도 같은 자세면 비슷한 값이 나온다.

완벽 호환은 아니다(검출 노이즈, 키포인트 정의 차이). 하지만
**"전혀 안 된다"가 아니라 "실기 검증 대상"**이다.

## 11. 로드맵에서 레포 통합을 누락 — **순서 오류**

### 경위
초기 로드맵에서 `board.py` 통합을 1단계로 뒀는데,
UX 우선으로 순서를 재조정하는 과정에서 조용히 사라졌다.

### 왜 문제인가
SPA shell(2단계)이 이 로드맵에서 **가장 덩치 큰 작업**이다.
통합 없이 진행하면 pibo에 한 번, pibrain에 한 번 만들게 되고,
**두 벌이 또 갈라지기 시작한다.**

지금 `tools/`가 pibo=socket.io / pibrain=REST+SSE로 아키텍처까지 달라진 게
정확히 그렇게 벌어진 결과다.

### 수정
**통합이 0단계.** UX 작업 앞에 온다.
